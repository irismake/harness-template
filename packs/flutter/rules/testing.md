# 테스트 (Flutter 팩)

## 구성

- `test/` 는 `lib/` 의 폴더 구조를 그대로 따른다. 파일 이름은 `<대상>_test.dart`.
- 공용 가짜 객체 · 픽스처는 `test/helpers/` (또는 프로젝트 규칙이 정한 위치)에 둔다.
- 통합 테스트(`integration_test/`)는 핵심 흐름만. 기기 · 에뮬레이터가 필요해 CI 에서 돌릴지는 프로젝트가 정한다.

## 무엇을 테스트하나 (우선순위)

1. **단위**: 도메인 로직 · 상태(뷰모델 · 노티파이어 · 블록) 전이 · 변환 · 저장소 매핑 · 오류 분기.
2. **위젯**: 상태별로 화면이 맞게 그려지는지(로딩 · 빈 상태 · 오류 · 데이터), 사용자 입력이 올바른 동작을 부르는지.
3. 골든 테스트는 플랫폼 · 글꼴에 따라 결과가 달라진다. 쓰기로 결정한 경우에만 쓴다.

## 규칙

- 테스트에서 실제 네트워크 · 실제 저장소 · 현재 시간에 기대지 않는다. 가짜 구현이나 목(프로젝트가 고른 도구)을 주입한다.
- 한 테스트는 한 동작만. 이름은 `'<조건>일 때 <기대 결과>'` 처럼 동작을 설명한다.
- `pumpAndSettle` 은 끝나지 않는 애니메이션에서 멈춘다. 필요한 만큼 `pump` 한다.
- 실패하는 테스트를 지우거나 `skip` 해서 통과시키지 않는다. 필요하면 이유를 적고 사용자에게 묻는다.
- **설정 값**(타임아웃 · 재시도 횟수 · 크기 제한 등)은 코드와 **같은 상수를 참조해** 비교한다 — 값을 테스트에 다시 적으면 한쪽만 바뀌어 어긋난다. (검사: `config-literal`, 켰을 때)
- **동작 결과**(변환 · 계산 · 파싱)의 기대값은 테스트에 **직접 적는다** — 구현의 상수 · 로직을 재사용하면 구현이 틀려도 같이 틀려 통과한다.

## 실행 (TDD)

- 관련 테스트만: `.harness/core/harness test test/<경로>_test.dart` (폴더도 된다). RED 는 **기대한 이유로** 실패하는지까지 확인한다.
- 전체 테스트(`harness test --all`)는 CI 가 한다. 사용자가 요청할 때만 로컬에서 실행한다.
- 테스트는 꼭 `harness test` 로 실행한다 (직접 `flutter test` 는 TDD Guard 기록이 남지 않는다). CI 는 PR 의 새 테스트를 변경 전 코드에서 실행해 실패하는지 다시 확인한다.
