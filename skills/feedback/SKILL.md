# 피드백 루프 (실수 → 재발 방지)

기록만 하고 끝내지 않는다. **다음에 같은 실수가 나면 자동으로 걸리게** 만드는 것이 완료 조건이다.

## 실행 조건

- 사용자가 에이전트의 실수 · 규칙 위반을 지적했다.
- reviewer · CI · 훅이 잡은 문제가 기존 로그와 같은 유형이다 (재발).
- 규칙 문서와 실제 코드가 다르다 (규칙이 틀렸거나 코드가 틀렸거나).

한 번뿐인 단순 오타 · 요구사항 오해는 대상이 아니다. 그 자리에서 고치고 끝낸다.

## 승격 기준 — 규칙 · 검사로 올릴지

하나 이상이면 **승격**한다. 아니면 로그에 `후보 → 기각` 으로만 남긴다 (일회성 실수로 규칙을 늘리지 않는다).

| 승격 대상 | 예 |
|---|---|
| 같은 유형이 두 번 이상 (로그 유형 열로 판단) | 같은 계층 위반이 다른 기능에서 또 나왔다 |
| 보안 위반 · 그 위험 (Secret · 인증 정보 · 권한) | 토큰을 로그에 넣었다 |
| 아키텍처 · 의존 규칙 위반 | domain 이 UI 를 import 했다 |
| 사용자가 확정한 기술 결정 | "앞으로 날짜는 UTC 로 저장한다" |

- 이미 있는 규칙을 안 지킨 것은 **새 규칙이 아니다** — 규칙을 더 쓰지 말고 강제 수단(검사 · 테스트)을 붙인다.
- **한 곳에만** 쓴다: 그 규칙을 소유하는 **가장 좁은** 문서 하나 (`paths` 가 가장 좁게 맞는 프로젝트 규칙 → `project.md` 순). 비슷한 규칙이 있으면 새로 쓰지 말고 **그 문장을 고친다**. `CLAUDE.md` · `AGENTS.md` 같은 어댑터에는 복사하지 않는다. (`check-rules` 가 규칙 문서 사이 같은 문장을 검출한다)

## 절차

1. **로그 확인**: `.harness/feedback-log.md` 에서 같은 유형(유형 열)이 있었는지 본다. 있으면 이번은 **재발**이다 — 기존 수단이 왜 못 막았는지부터 적는다.
2. **원인 분류**: 규칙이 없었다 / 규칙은 있었지만 강제가 없었다 / 규칙이 틀렸다(실제 코드와 다름) / 규칙이 로드되지 않았다(`paths` 누락) / 검사에 구멍이 있었다.
3. **수단 선택** — 위에서부터 가능한 것을 고른다. **프로젝트 안에서 고칠 수 있는 곳만 쓴다** (`.harness/core/` 는 고치지 않는다).

   | 우선 | 수단 | 언제 |
   |---|---|---|
   | 1 | 결정적 검사: `config.json` (`layers` 금지 import · `protected` 차단 패턴 · `secret_files`) · 프로젝트 검사 `.harness/checks.py` · 린트 설정(예: `analysis_options.yaml`) | 코드 · 명령 · 경로 패턴으로 판정할 수 있다 |
   | 2 | 회귀 테스트 | 동작으로 고정할 수 있다 (버그 · 경계 조건) |
   | 3 | 규칙 문구 (`.harness/rules/*.md`) · `paths` 보강 → `harness sync` | 판단이 필요해 자동 검사가 어렵다 |
   | 4 | 로그만 | 위 셋 모두 불가 — 이유를 반드시 적는다 |
   | T | 템플릿 레포(irismake/harness-template)에 이슈 · PR 제안 | 코어 · 팩 규칙 · 검사가 틀렸거나 모든 프로젝트에 해당 |

   - 규칙이 실제 코드와 다르면 코드가 아니라 **규칙을 코드에 맞춘다** (코드를 바꿔야 한다면 사용자에게 묻는다).
   - 검사 · 설정 · 규칙 변경은 하네스 변경이라 **사용자 승인 후** 반영한다 (Claude 는 훅이 확인 창을 띄운다).
   - `.harness/checks.py` 형식: `def check(ctx):` 에서 `ctx.added` (`{경로: [(줄, 내용)]}`) · `ctx.new` 를 보고 `ctx.report(규칙ID, 경로, 줄, 메시지, 규칙 파일)` 을 부른다. 예시는 `.harness/core/packs/<팩>/checks.py`.
4. **반영 · 확인**: 수단을 추가하고, 일부러 같은 실수를 만든 임시 변경으로 **실제로 잡히는지** 확인한 뒤 지운다. 기존 위반이 있으면 고칠지 사용자에게 묻는다.
5. **기록**: `.harness/feedback-log.md` 표에 한 줄 추가한다. 확인 열에 `승격` · `후보 → 기각(이유)` 을 함께 적는다.

## 출력 (보고)

- 무엇이 잘못됐나 · 원인 분류 · 재발 여부
- 고른 수단과 이유 (상위 수단을 못 쓴 이유 포함)
- 잡히는지 확인한 방법 · 결과

## 완료 조건

- 로그에 기록됐고, 수단이 1~3 중 하나면 같은 실수를 만들었을 때 실제로 걸리는 것을 확인했다.
