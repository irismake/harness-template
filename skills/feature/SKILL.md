# 기능 구현 (TDD)

## 입력

사용자 요청. 있으면 디자인 · API 스펙 · 관련 화면.

## 절차

0. **설계 확인**: `config.json` `design_done` 이 `false` 면 멈추고 `project-design` 부터 한다.
1. **경로 판정** (`core.md` "작업 경로 · 역할") → `.harness/core/harness work lane <S|M|L>` 로 선언한다 (위험 영역 · 계층 두 곳 이상 · planner 사용이면 하네스가 L 로 올린다). L 이면 `planner` 를 부르고 한 줄 결과의 `plan.md` 를 읽어 사용자 승인을 받는다. M 이면 계획을 3~5줄로 공유한다.
2. **브랜치**: 보호 브랜치에 있으면 `base_branch` 에서 `feat/<kebab-case>` 를 만든다. 리팩토링은 `refactor/`.
3. **기존 구조 찾기**: 가장 비슷한 기존 기능을 찾아 같은 폴더 · 이름 · 조립 방식을 따른다. 첫 기능이면 `architecture` 규칙의 구조를 따른다.
4. **RED**: 고정할 동작(도메인 로직 · 상태 전이 · 변환 · 저장소 매핑 · 오류 분기)마다 실패하는 테스트를 쓴다.
   - **요구사항 추적이 켜져 있으면**(`config.json` `trace.enabled`) 테스트보다 먼저 문서에 적는다: 요구사항 문서에 REQ, 시나리오 문서 표에 `| TS ID | REQ ID | 시나리오 (Given / When / Then) | … |`. 테스트에는 시나리오 ID 를 프로젝트 방식(`trace.test_marker`)으로 붙인다 — 시나리오 하나 = 테스트 하나. 아직 테스트를 쓰지 않은 문서 단계면 문서 상단 `> 상태:` 에 `구현 전` 을 두고, 구현이 끝나면 지운다. 연결은 `harness trace` 로 확인한다.
   - 테스트는 대상 파일을 **import** 하거나 규칙상 짝 경로(`test/…/<이름>_test.dart`)에 둔다 — TDD Guard 가 이것으로 테스트와 코드를 연결한다.
   - `.harness/core/harness test <테스트 파일>` 로 **기대한 이유로** 실패하는지 확인한다 (컴파일 오류만으로 RED 를 끝내지 않는다).
   - 새 타입이면: 테스트 → 실행(컴파일 실패) → 골격(빈 구현) → 실행(**동작 실패** = behavior RED) 순서로 간다.
   - 리팩토링은 반대로 시작한다: 지금 동작을 고정하는 테스트가 없으면 먼저 추가해 GREEN 에서 출발한다.
   - **TDD Guard 가 켜져 있으면**(`config.json` `tdd.enabled`) 대상 기능 코드는 연결된 테스트의 RED 기록이 있어야 고칠 수 있다 (Claude 는 실행 전 훅이 막는다). 완료(종료 전 · 커밋)에는 behavior RED → GREEN 기록(같은 테스트로 실패 → 연결된 구현이 바뀌어 통과. 테스트 포맷 정리 · import 경로 변경 · 같은 사이클의 선언 파일은 괜찮다)과 "GREEN 이후 바뀌지 않음" 이 필요하다. Bash 로 대상 코드를 바꿔도 실행 후 훅이 잡는다. 상태: `harness tdd status`.
   - Guard 가 "RED 미확인" · "연결된 테스트가 없다" 로 막으면 **이미 통과하는 테스트를 덧붙여 넘기지 않는다** — 테스트 없이 쓴 구현을 지우고(되돌리고) 테스트 → RED → 구현 순서로 다시 하거나, 아래 예외 승인을 요청한다.
   - 테스트로 고정할 동작이 정말 없으면(동작 변화 없는 리팩토링 · 생성 코드 연결 등) 이유를 들어 **사용자에게** `harness tdd skip <파일> --reason …` 승인을 요청한다. 스스로 예외를 만들지 않는다.
5. **GREEN**: 테스트를 통과시키는 최소 구현 → 같은 명령으로 통과 확인.
6. **REFACTOR**: 규칙(아키텍처 · 상태 관리 · UI 등)에 맞게 정리 → 다시 통과 확인.
7. **마무리 검증**: `.harness/core/harness verify`. 위반은 고치거나 이유를 보고한다. 전체 테스트 · 빌드는 CI 가 한다.
8. **기능 목록 갱신**: `project.md` "기능 목록" 의 상태를 바꾼다.
9. **L 이면 `reviewer`** 에게 요구사항(계획 경로)과 기준 ref(`base_branch`)만 넘긴다. 한 줄 결과가 FIX_REQUIRED 면 보고서의 **발견 사항 · 미검증만** 읽고 **지적한 것만** 고친다 → 다시 `reviewer`(이전 보고서 경로를 함께) — 최대 3라운드, PASS 면 바로 끝낸다. 3라운드 뒤에도 남으면 남은 지적 · 시도한 것을 사용자에게 보고한다. 반영하지 않은 지적은 이유를 남긴다.

테스트로 고정할 동작이 없는 순수 레이아웃 변경은 4~6 을 생략할 수 있다. 생략했으면 보고에 적는다.

## 출력 (보고)

- 바꾼 파일과 이유 (계층별)
- 요구사항별 충족 여부
- 실행한 테스트: RED 확인 → GREEN 결과 (실행하지 않았으면 그렇다고). 전체 테스트는 CI 에서 확인된다고 적는다
- 새로 필요한 패키지 · 결정 변경 · 사용자에게 물을 것

## 완료 조건

- 요구사항을 모두 충족했거나, 못 한 항목과 이유를 보고했다.
- 추가 · 수정한 테스트가 실제 실행 결과로 통과했고, `verify` 를 통과했다.
- L 이면 reviewer 최신 판정이 PASS 이거나, 3라운드 뒤 남은 지적과 미반영 이유를 보고했다. (push 할 때 하네스가 PASS · 리뷰 뒤 소스 불변 · 테스트 기록을 다시 확인한다)
- 커밋 · PR 은 사용자가 요청할 때 `pr` 스킬로 한다.
